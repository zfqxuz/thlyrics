# 评审邀请：用户交互 + 页面布局（给 Codex / Claude 的提示词）

> 用途：把下面「提示词正文」整段复制给 Codex 或 Claude（它们能读仓库 / 能跑命令效果最好）。
> 目标不是让它改代码，而是**拿到一批能落地的交互与布局改进意见**；改不改由我们决定。
> 本文件放着两份：A. 给 Codex（能跑仓库、能出 patch）；B. 给 Claude（偏交互/设计评审）。

---

## A. 给 Codex 的提示词（可执行、可出 patch）

````text
你是一位移动端 Web/App 的资深前端 + 交互工程师。请对下面这个项目做一次「用户交互 + 页面布局」评审，并给出可直接落地的改动建议（能顺手给出 patch 更好）。

## 项目是什么
「TH Lyrics」——东方同人曲的**学唱工具**（个人自用，不传播、不商用）：
把日文歌词切成词，给出读音（假名/罗马音）与中文释义，支持跟唱（单句循环、倍速、逐词中文），
曲库来自用户自己导入的网易云/QQ 音乐链接（本站不内置曲目）。既是网页（GitHub Pages 静态站），
也打包成安卓 App（Capacitor 壳 + 原生 MediaSession/前台服务）。

## 硬约束（不要提出违反它们的方案）
1. 词汇入手：首页围绕「学哪些词」组织，不是「先给一首歌的完整歌词」。
2. 标日对照：每个词要有《标准日本语》课次/难度分级。
3. 交互顺畅：播放器要有缓冲/预加载；点词、单句循环、倍速、上下句要丝滑；**点词不能冒泡成切句**。
4. 歌词可视化：同一句里不同词性不同颜色；中文释义要能落到**词级**（不是只有整行翻译）。
5. 纯工具向：不做打卡/连续天数那套。进度存 localStorage，可导出导入。
6. 内容冻结：**不要新增/翻译任何歌词内容或词条数据**；改动只允许在 `docs/` 前端与 `scripts/` 逻辑里。
7. 视觉语言已定：墨蓝底 + 暖白纸 + 一点朱红（`--accent:#d4503c`），**不用渐变、发光、玻璃拟态**；
   字号只用 6 档、间距只用 5 档（见 `docs/index.html` 顶部 `:root`）。
8. 线上是 `docs/` 目录直接发布（纯静态、无打包器、无框架）；不要引入 React/Vue/构建链。
9. 现有行为契约不要打破（有 E2E 守着）：抽屉（`#pop`）的关闭方式、点词只对当前句生效、
   媒体键 = 上一首/下一首（不是上一句/下一句）、单句/全曲开关、播放顺序（顺序/循环/随机）。

## 代码在哪、怎么跑
- 前端全部在 `docs/`：`docs/index.html`（HTML + 全部 CSS + 玩家页/抽屉的 DOM）、`docs/app.js`（约 2700 行，原生 DOM）、`docs/platform/*`（平台适配层）。
- 本地跑：`node scripts/serve.mjs 8848` → http://127.0.0.1:8848/ （需要先注册一个本地账号，闸门是账号制）。
- 自检 / 回归：`node .e2e/run-e2e.mjs`（Playwright，170+ 条；夹具在 `.e2e/fixture-index.json`，
  截图落在 `.e2e/shots/`）。**改完必须 170+ 全绿。**
- 手机尺寸验收：Playwright 视口 400×850（真机是华为 Android 10 的 WebView + 电容壳）。
- 安卓壳：`app/`（Capacitor），出 APK 用 `app/android/gradlew assembleDebug`。

## 重点评审这几处（按优先级）
1. **跟唱页（全屏播放器 `#player`）**：头部 / 歌词区 / 控件区的信息层级与拇指可达性；
   `#p-scope`（单句⇄全曲，一个开关两边显示）、`#p-order`（顺序/循环/随机）、`#b-display`（⋯ 里的显示开关：倍速/词义/整句中文/逐词罗马音）、`#p-seek`。
2. **点词抽屉 `#pop`**：弹层内容多（释义/例句/罗马音编辑/更多），信息层级是否清楚；关闭手势是否够直觉。
3. **歌词排版**：一行里「罗马音在上 / 日语居中 / 中文在下」的三层排版，长句换行、标点错位、行高抖动；
   当前句高亮 + 自动滚动是否让人能一直跟住。
4. **曲库 / 导入流程**：导入网易云/QQ 歌单/专辑/单曲链接、失败与「跳过」的反馈、专辑网格。
5. **首次上手**：注册闸门 → 首页（今天学哪些词）→ 挑歌 → 跟唱，这条路有没有多余的点击/黑话。
6. **手机细节**：安全区（刘海/手势条）、320px 窄屏、横屏、键盘弹起（抽屉/输入框）、触摸目标 ≥ 40px。

## 输出要求（中文）
1. **结论先行**：只挑「最值得改的 3 件事」，说明为什么是这 3 件（各一句）。
2. **问题清单**：每条写成 `现象 → 证据（文件:行号 / 选择器 / 截图） → 对用户的影响 → 建议改法 → 工作量(S/M/L)`；
   按影响×性价比排序，最多 12 条，不要凑数。
3. **可直接落地的改动**：给出具体选择器/函数名/行号，或直接给 patch（保持现有代码风格：原生 DOM + 模板字符串 + 中文注释）。
4. **不要做的事**：明确列出你认为「看起来该改但其实不该动」的地方（例如有 E2E 契约、或会加重认知负担的）。
5. 如果能跑仓库：附上 400×850 与 320×600 两张截图（改前/改后），并贴 `node .e2e/run-e2e.mjs` 的结果行。

## 请不要
- 不要提「加骨架屏 / 加动画 / 换框架 / 上设计系统」这类大而空的建议，除非能给出具体的最小实现。
- 不要新增任何歌词/词条内容。
- 不要破坏上面的硬约束与已知契约。
````

## B. 给 Claude 的提示词（偏交互与视觉评审）

````text
你是一位做过大量真实产品迭代的交互设计师 / 可用性评审员。我做一个「日语学唱工具」，想请你以**挑剔的用户**视角评审它的交互与页面布局，并给出可执行的改进。

## 产品一句话
「TH Lyrics」：东方同人曲的学唱机。把日文歌词按词切开，标读音（假名 + 罗马音）、按词性配色，
每个词能点开看释义和例句；跟唱页支持逐句循环、倍速、逐词中文、整句中文。
曲库由用户自己导入（网易云/QQ 音乐链接），既是网页版也有安卓 App（自用、不传播）。

## 用户是谁
- 中文母语、在学日语（初级~中级）、爱东方同人曲，主要用手机（安卓 WebView / 电容壳），常在**碎片时间**跟唱练句。
- 已经明确反馈过几次：「点词弹层影响别的句子」「中文逐词翻译不准」「播放控制不顺手」——他很在意交互的确定性。

## 现在的交互契约（已与用户确认，评审时请当成前提）
- 点词：**只对当前这一句生效**；想查别的句的词，先把那一句切过来。
- 抽屉：点外部关闭 / 下拉关闭 / ✕ 关闭；关闭那一下**不许穿透**到下面的歌词（不能顺手跳句）。
- 抽屉一弹出就暂停播放，收起抽屉才继续播。
- 播放控制：`全曲 ⇄ 单句` 是一个开关（两边都显示，点一下换边）；
  播放顺序是 `顺序 / 循环 / 随机` 三档；倍速和显示开关收在「⋯」里。
- 媒体键（锁屏/通知栏）＝上一首 / 下一首；页内的「上一句 / 下一句」＝歌词行导航。

## 请你评审
1. 跟唱页（全屏播放器）的**信息层级与拇指操作**：头部（封面/曲名/收起）、歌词区、底部控件区，
   哪个按钮该更大、哪个该收起来、哪个位置放错了？
2. 「三层歌词排版」（罗马音在上 / 日语居中 / 中文在下）+ 当前句高亮 + 自动滚动：读起来累不累？哪里会眼花？
3. 点词抽屉：内容多（词/读音/罗马音/释义/词性/难度/例句/罗马音纠正/改释义/标掌握/去这句），
   打开后第一眼应该看到什么？哪些应该藏在「更多」里？
4. 播放控制区：`全曲/单句` 开关 + `顺序/循环/随机` + 倍速 + 显示开关，摆成什么样最不用想？
5. 首次上手路径：注册 → 首页「今天学这几个词」→ 挑歌 → 跟唱，哪里让人懵？
6. 手机细节：安全区、单手可达性、误触（歌词太密导致点错句）、键盘弹起。

## 输出要求（中文，别写虚的）
1. 「如果只能改 3 处」——排好序，每处写：改什么 / 用户会怎么感觉到 / 为什么现在这样不好。
2. 逐屏走查：按 `首页 → 曲库 → 单曲页 → 跟唱页 → 点词抽屉 → 生词本`，每屏写
   「第一眼看到什么 / 想干什么 / 卡在哪」，每条不超过 3 行。
3. 具体建议：用「位置 + 改成什么 + 为什么」写，能画 ASCII 线框图就画（底栏、抽屉、歌词行各一张）。
4. 反例清单：现在哪些设计**不要改**（改了会更糟），以及哪些是「加功能就能解决，但其实该减」。

## 边界
- 视觉语言已定：墨蓝 + 暖白 + 朱红，不用渐变/发光/玻璃拟态；字号 6 档、间距 5 档。
- 不做打卡/连续天数/社交这类跑偏的功能。
- 不要建议新增歌词或翻译内容。
````
